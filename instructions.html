Administrator Documentation

How this site works

This guide covers what the site is, how the files fit together, and exactly how to set up the Google / Firebase configuration so the Events schedule pulls live from a database instead of being edited in code. Everything here can be done from a web browser — no software to install.

The short version. Add event documents to the events collection in the Firebase console. The site picks them up within a second or two, with no redeploy. If the database is empty or unreachable, the site quietly falls back to a built-in schedule so visitors never see a broken page.

1. What this site is

A public information site for the Diocesan Commission for Filipino Catholics of the Roman Catholic Diocese of San Diego. It presents the Commission’s identity and mission, its annual liturgical celebrations, photographs and recordings of community life, downloadable documents and registration forms, and contact details for its officers.

It is a static site — plain HTML files hosted on GitHub Pages. There is no server to maintain and no hosting bill. The only moving part is the events database described below.

How the Events section behaves

  • Next Celebration — the card beside the Events heading. It is not hand-written; the site picks the soonest event whose date has not yet passed and shows it. A celebration disappears from the card automatically about six hours after it begins.
  • Diocesan Event Schedule — the grid revealed by the View Schedule button, listing every published event in date order.
  • Status line — a small line beneath the grid says whether the list came from the live calendar or from the built-in fallback. Use it to confirm your setup is working.
  • Sign in — at the top right of every page, beside the navigation, showing an anonymous avatar until someone signs in and their Google profile picture afterwards, with the label switching to Sign out. Visitors can ignore it; staff on the allow list sign in there and get a form under Events to add, edit, and delete celebrations directly on the page.

Nothing about the editing interface is trusted for security. It only decides what to show; the Firestore rules decide what is allowed. Somebody who edited the page in their own browser to reveal the form would still have every save refused.

2. Set up Firebase Firestore

The site is already pointed at the Firebase project dcfc-data. These steps create the database it reads from. Do them once.

Step 1 — Create the database

  1. Go to console.firebase.google.com and sign in with the Google account that owns the project.
  2. Open the dcfc-data project.
  3. In the left sidebar choose Build → Firestore Database, then Create database.
  4. Choose Start in production mode. (You will paste proper rules in Step 2, so test mode is unnecessary and expires after 30 days.)
  5. For location choose nam5 (us-central) or us-west2. This cannot be changed later, but either is fine for a San Diego audience.
  6. Click Create and wait for provisioning to finish.

Step 2 — Publish the security rules

Rules decide who may read and write, and they are the only real protection on your data — the allow list inside index.html merely controls what the interface offers. Both must list the same people.

These rules allow anyone to read events (the site is public) but permit writes only from a signed-in Google account whose user ID appears in the allow list, and close off every other collection. In Firestore, open the Rules tab, select all the existing text, paste this over it, and click Publish.

Firestore security rules 
rules_version = '2';

service cloud.firestore {
  match /databases/{database}/documents {

    // ---------------------------------------------------------------
    // ADMINISTRATOR ALLOW LIST
    // Paste each administrator's Firebase UID between the quotes.
    // Add or remove lines as people join and leave the Commission.
    // The SAME list must also appear in adminUids in index.html.
    // ---------------------------------------------------------------
    function admins() {
      return [
        "29fwr8BEMIMpA8a3wlT3cPLLIts1",
        "XLj2RJN2hIWEHboGzIl2uFSLpiU2"
      ];
    }

    function isAdmin() {
      return request.auth != null
          && request.auth.uid in admins()
          && request.auth.token.email_verified == true;
    }

    // Events shown in the public schedule.
    // Anyone may read. Only an administrator on the list may change them.
    match /events/{eventId} {
      allow read: if true;
      allow create, update, delete: if isAdmin();
    }

    // Site settings, e.g. the Santacruzan registration open/close dates.
    // Anyone may read. Only an administrator on the list may change them.
    match /settings/{settingId} {
      allow read: if true;
      allow write: if isAdmin();
    }

    // Everything else is closed until it is explicitly opened.
    match /{document=**} {
      allow read, write: if false;
    }
  }
}

The two IDs above are the current administrators and match adminUids in index.html. Publish as written. Step 4 explains how to obtain an ID for anyone you add later — it goes in both lists.

Why the API key in the site is safe to publish. A Firebase web API key is an identifier, not a password — it appears in the source of every Firebase site on the web. Your data is protected by the rules above, which is why they matter and why the catch-all deny is there.

Step 3 — Turn on Google sign-in

  1. In the Firebase console, go to Build → Authentication and click Get started.
  2. On the Sign-in method tab choose Google from the provider list.
  3. Switch it to Enable, pick a support email, and click Save. No other provider is needed — administrators sign in with their Gmail or Google Workspace account.
  4. Open the Settings tab, then Authorized domains. Add your GitHub Pages hostname, e.g. yourname.github.io, plus any custom domain. localhost is already there for testing.

If you skip the Authorized domains step, sign-in fails with “This web address is not on the Authorized domains list” — the site reports this on screen.

Step 4 — Add administrators to the allow list

Each administrator’s Firebase UID is a unique identifier generated the first time they sign in. You cannot invent it or look it up in advance — they must sign in once so the site can show it to them.

  1. Have the administrator open the site and click Sign in at the top right.
  2. They sign in with their Google account. Because their ID is not on the list yet, the site says Not yet authorized and displays their user ID with a Copy my ID button.
  3. They send you that ID. Paste it into both places:
    • Firestore rules — replace a PASTE_..._UID_HERE placeholder inside admins(), then Publish. This is what actually grants access.
    • index.html — find adminUids near the top of the script at the bottom of the file and add the ID as a quoted string, e.g. "abc123XYZ",. Remove the leading // from the sample line. This is what reveals the editing interface. Commit and push.
  4. The administrator signs out and back in. They now see Calendar Administration with the event form and the list of published celebrations.

Both lists, every time. In the rules only → they can write but see no interface. In index.html only → they see the form but every save is refused with a permissions error. To revoke access, remove the ID from both and publish; that person is locked out immediately, regardless of what is cached in their browser.

Step 5 — Create the events collection

  1. In Firestore, open the Data tab and click Start collection.
  2. Set the Collection ID to exactly events — lower case, plural.
  3. Firestore will ask for a first document. Click Auto-ID for the Document ID and add the fields from the table below.
  4. Click Save, then reload the public site and open View Schedule. Your event should appear and the status line should read “Live from the Commission’s diocesan calendar.”

Event fields

FieldTypeMeaning
title required string Name of the celebration, e.g. Feast of San Lorenzo Ruiz.
start required timestamp Date and time it begins. This is what the site sorts by and what makes an event count as upcoming or past, so it must be a real timestamp, not a string.
parish recommended string Host parish, e.g. St. Mary Church, National City.
address optional string Street address. Omitted from the card when blank.
time recommended string Human-readable schedule of the day, e.g. 9:15 AM rosary · 10:00 AM Mass. Written out rather than derived, so processions and multiple Masses read naturally.
detail optional string Celebrant, guest speaker, notes to parish delegations. Shown as a footnote on the card.
end optional timestamp Only for multi-day observances such as Simbang Gabi. When present, the date reads as a range and the event stays “upcoming” until the last day.
dateLabel optional string Overrides the automatically formatted date with your own wording, e.g. Nine dawn Masses, December 15–23. Leave it off unless the automatic label reads badly.
published optional boolean Set to false to draft an event without showing it publicly. Anything else, or absent, is treated as published.

Entering a timestamp. In the Firebase console, choose timestamp as the field type and a date-and-time picker appears. Set the time to when the celebration actually begins — the procession or first Mass — because that is what orders the schedule.

Step 6 — Add the rest of the year

Once you are on the allow list, the quickest way to work is on the site itself: sign in, fill in the form under Events, and click Add to calendar. Each entry in the Published calendar list beside it has Edit and Delete. Changes appear for every visitor immediately, with no republishing.

The Firebase console remains available for the same job and is the better place for bulk work. Order does not matter either way; the site sorts by start.

Untick Visible on the public schedule to draft an event that only administrators can see — useful while a host parish or celebrant is unconfirmed.

The Host parish field suggests churches as you type. It holds 107 churches of the diocese — parishes and missions together; type a few letters of the name or the city, then click a suggestion or use the arrow keys and Enter. Selecting one fills in the Address field for you. Both fields stay editable — overwrite them for a venue that is not a parish, or to add a suite number or ZIP. A handful of missions have no street address on file, so the address arrives as city only; type the rest. The list lives in parishes near the top of the script in index.html if a parish moves or is renamed.

About that roster. The diocese publishes a count of 96 parishes and 13 missions, but does not publish a single machine-readable list of them; this one was compiled from the diocesan parish directory and comes to 107 entries, without marking which are parishes and which are missions. It is close but not authoritative. If an administrator reports a missing church, add a line to parishes — ["Name", "City", "Street"] — and reconcile against sdcatholic.org/find-a-parish.

3. Hosting on GitHub Pages

  1. Commit every file — index.html, support.js, and the whole Assets folder — to the repository root. This guide is deliberately excluded by .gitignore; keep a copy somewhere your successors will find it.
  2. In the repository, open Settings → Pages.
  3. Under Source, choose Deploy from a branch, then branch main and folder / (root). Save.
  4. Wait a minute, then visit the URL GitHub shows. Because the home page is named index.html, it loads at the bare address with nothing after the slash.

Two things that will bite you. File names are case-sensitive on GitHub Pages but not on a Mac — assets/Images/DCFC_LOGO.png must match exactly. And if you ever add a folder beginning with an underscore, add an empty .nojekyll file at the root so GitHub does not skip it.

4. Documents and forms

The Documents & Forms view lists files by hand, in index.html. To publish a new flyer or guideline:

  1. Add the PDF to files/Documents/.
  2. Open index.html and find the groupDefs list near the bottom of the file, then the section for the right observance (featuredItems, just above it, holds the Event Schedule and Host Parish Registration).
  3. Copy an existing entry and change its title, description, meta, and href. The href is the path to your file, e.g. files/Documents/YourFlyer.pdf.
  4. Set kind to "doc" for a document or "form" for a form, then commit. A section with no items shows “Nothing posted yet”.

The Santacruzan registration form expects a Google Apps Script endpoint to receive submissions. If it shows a setup banner, open files/Forms/santacruzan-registration.html, find SCRIPT_URL near the bottom, and paste in the Web App URL of your deployed Apps Script — created from a Google Sheet via Extensions → Apps Script, then Deploy → New deployment → Web app, with access set to Anyone.

5. If something looks wrong

SymptomCause and fix
Status line says the live calendar could not be reached, with permission-denied The security rules were not published, or the read rule is missing. Redo Step 2.
Status line says nothing has been published yet The events collection is missing, misspelled, or every document has published: false. Collection names are case-sensitive.
Status line says the live calendar has not been set up yet The site reached out but got no answer within nine seconds — almost always because the Firestore database itself has not been created. Do Step 1, then Steps 2 and 3.
An event is missing or out of order Its start field is a string rather than a timestamp. Delete the field and re-add it with type timestamp.
Next Celebration shows a past event Every event’s date has passed. Add the coming year’s celebrations; the card then advances on its own.
Sign-in window opens then closes with an error Google sign-in is not enabled (Step 3), or the site’s address is missing from Authentication → Settings → Authorized domains. The on-screen message names which.
Signed in, but no editing interface appears The user ID is not in adminUids in index.html, or the change was not pushed to GitHub. Sign out and back in after pushing.
Saving an event fails with a permissions error The user ID is in index.html but not in the admins() list in the Firestore rules — or the rules were edited but not published.
Nothing happens when clicking Sign in The browser blocked the pop-up window. Allow pop-ups for the site and try again.
The date reads awkwardly Add a dateLabel with the exact wording you want.
Images or the schedule fail only on the live site Almost always a file-name capitalization mismatch. Compare the path in index.html against the file in the repository, character for character.
